# Laravel 13 更新・運用計画

## 更新内容と互換性

Laravel 5.8.31 から Laravel 13 へ移行し、認証、パスワード再設定、投稿・コメント、ユーザーページを現在の Laravel API に合わせました。ログインは従来どおりメールアドレスを使い、ニックネームは登録・プロフィール表示に使います。投稿者だけが投稿を編集・削除でき、投稿・コメント本文と画像 URL を検証します。画像は `http` または `https` の URL のみ受け付け、既存レコードの URL も表示時に再検証します。

Laravel 13 は PHP 8.3 以上が必要です。フレームワークがサポートする DB の最低バージョンは MySQL 5.7、MariaDB 10.3、PostgreSQL 10、SQLite 3.26、SQL Server 2017 です。アプリケーションは PHP 8.3 / SQLite でローカル検証済みです。CI は PHP 8.3 と 8.4 の両方を実行する設定ですが、PHP 8.4 の実行結果は CI の完了後に確認してください。実運用 MySQL と実 SMTP への接続確認は行っていません。

6 件の既存マイグレーションファイルは変更しておらず、新しいスキーマ変更も追加していません。`users`、`tweets`、`comments`、`password_resets` のテーブルと既存行を維持する設計です。既存のパスワードハッシュはそのまま使用します。Laravel 13 のセッション JSON シリアライズ設定により、更新前のログインセッションは引き継がれず、利用者は再ログインが必要です。

## 新規の開発環境

新しいローカル環境でのみ、次の手順でキーを生成して SQLite スキーマを作成します。

```sh
composer install
cp .env.example .env
php artisan key:generate
touch database/database.sqlite
php artisan migrate
php artisan serve
```

既定の SQLite ファイルは `database/database.sqlite` です。MySQL などを使う場合は `.env` に接続情報を設定してから `php artisan migrate` を実行します。

## 既存環境の更新

1. メンテナンス時間を調整し、データベースの整合性が取れたバックアップと、現在のリリース一式を保存します。デプロイ用 `.env` または環境変数の安全なコピーも確保します。
2. `.env` を新しい `.env.example` で上書きせず、既存値を保ったまま必要な設定だけを確認します。特に `APP_KEY` は現行値を保持してください。再生成すると暗号化データとログインセッションに影響します。
3. PHP 8.3 以上を用意し、新しいコードを配置します。依存関係をロックファイルどおりにインストールします。

   ```sh
   composer install --no-dev --prefer-dist --optimize-autoloader --no-interaction
   ```

4. `APP_ENV=production`、`APP_DEBUG=false`、実際の HTTPS `APP_URL`、公開するホスト名だけを含む `TRUSTED_HOSTS`、本番 DB 接続、実 SMTP 設定を確認します。HTTPS を使う場合は `SESSION_SECURE_COOKIE=true` を設定してください。複数台構成ではセッションとキャッシュに共有ストアを設定してください。
5. アプリケーションから対象 DB へ接続できることを確認し、`php artisan migrate:status` を実行します。この更新には新しいマイグレーションがありません。既存の 6 件が適用済みであることを確認し、未適用表示がある場合は、その理由を調査するまで本番マイグレーションを実行しないでください。
6. 必要な保守ウィンドウ内で設定・ルート・ビューキャッシュを作り直し、ログイン、投稿一覧、投稿詳細、コメント、画像、パスワード再設定をスモークテストします。

   ```sh
   php artisan optimize:clear
   php artisan config:cache
   php artisan route:cache
   php artisan view:cache
   ```

   監視とエラーログを確認してからメンテナンス状態を解除します。ログインセッションは再確立されるため、利用者に再ログインを案内します。

本番 DB で `migrate:fresh`、`db:wipe`、無確認の `migrate:rollback` を実行しないでください。これらは既存データまたは適用済みスキーマを失う可能性があります。今回のコードに DB 変更はありません。将来マイグレーションが追加される場合は、内容とバックアップをレビューしてから別の変更として実行してください。

## ロールバック

問題が発生した場合は、保存してある直前のアプリケーションリリースへ戻し、現在の `.env` と `APP_KEY` を維持します。この更新では DB スキーマを変更していないため、通常は DB 復元を行いません。問題発生後に別のマイグレーションを実行した場合は、アプリを戻す前に、その変更内容と書き込み状況を評価してください。DB 復元が必要な場合は、復元で更新後の利用者データも巻き戻るため、バックアップ時刻と以後の書き込みを確認してから実施します。
